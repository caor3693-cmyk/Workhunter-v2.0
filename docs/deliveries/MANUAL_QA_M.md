# M 阶段手工核验（当前版）

命名与页面要求更新：2026-10-11。阶段及人工核验统一M0—M4，原S/G按[映射](M_NAMING.md)追溯；原手工核验文件保留合同/历史记录。当前共37项，分阶段7/8/8/6/8；M0-07为本次新增，其他原检查点位置不变。用户当前结果见[M0反馈汇报](M0-FEEDBACK-20261011.md)。最终成品主页保持简洁，核验/开发材料不占主页，来源与核验采用独立子页。

本文件供开发者交付和负责人逐项核验使用。首版范围以 PRODUCT.md 为准；技术验收沿用 CONTRACTS.md、TASKS.md 的 A01—A12。本周先在 Site 使用，M4 完成前不切换正式站。

## 1. 顺序与判定

| 阶段 | 计划日 | 工作包 | 手工核验门 |
| --- | --- | --- | --- |
| M0 | D1 | W00：Site 入口与工程骨架 | M0 |
| M1 | D2—D3 | W01＋W02：两校真实流程 | M1 |
| M2 | D4—D5 | W03＋W04：十校与维护 | M2 |
| M3 | D6 | W05：持续运行 | M3 |
| M4 | D7 | W06：最终验收 | M4 |

计划日是安排，不是自动完成日。按 M0 → M1 → M2 → M3 → M4 核验；上门未通过时，后门可以准备材料，不能标成已通过或关闭。互不冲突的开发可以继续。

每项只使用四种用户结论：**通过、失败、阻塞、未测**。构建者不得替用户预填“通过”。未反馈、未测、环境不可达和只完成自动测试都不等于通过。

- 失败：能操作，但实际行为与预期不符。
- 阻塞：当前缺入口、材料、权限或必要环境，无法判断。
- 受限学校符合 Q5A：正确保留学校、显示受限状态、提供官方材料补录，其他学校可用，可以通过该“状态处理”用例；该校自动采集仍记受限，不能改记自动覆盖成功。
- 当前门的失败项必须修复并由用户按原编号复验。P0/P1 阻塞相应 Gate 与最终上线；首版内其他未解决反馈也不能自行降级后宣布全部完成。范围变更须有负责人明确决定和关联记录。

## 2. 每次交付一个可核验包

构建者更新当前 Gate 的既有 Issue，按 stage-review 模板补齐下列内容；只有该 Gate 尚无 Issue 时才新建，不能每次交付都重复建一张阶段单。缺项先补齐，不让用户查 SQL、运行服务器命令或寻找测试材料。

| 必填项 | 应提供的具体内容 |
| --- | --- |
| 身份与入口 | Gate、阶段、原功能 Issue、Site URL、是否需维护者身份，以及核验时间 |
| 构建 | 产品版本、完整 commit、对应 PR/提交；核验过程中换构建须明确说明 |
| 数据 | dataset_id、数据模式（真实官方来源/隔离回归样例/演示/空库）、观察或冻结时间；混用多套数据逐项标明 |
| 场景材料 | 每个编号对应的页面/记录、官方原文或获授权的隔离材料、所需初始状态；不能只有一串测试编号 |
| 构建者自验 | 真实做过的操作、结果、证据链接和未通过/未执行项；区分自动测试、真实采集、Site 浏览器和后端运行证据 |
| 用户操作 | 从本文件复制本门步骤，为每项补上具体材料和入口，保持原编号、操作及预期 |
| 回归与阻塞 | 上一 Gate 结论链接、关联反馈 Issue、修复版本、仍需复验项和外部限制 |
| 反馈格式 | 第 3 节模板；用户逐项回，不预勾通过 |

构建身份放在核验包或维护诊断中，不加进招聘卡片。正常浏览期间数据会更新时，构建者记录用户实际查看的数据版本；分页变更行为应符合合同，不能把两个版本拼在一起作证。

Site 上的演示数据可以验证界面，不能证明真实采集、持久化、定时刷新或权限隔离。隔离回归样例须有明显说明，并与实际数据分开。M1 起的主流程必须有真实官方材料与实际入库证据；反例可由开发者准备隔离场景供用户点选，不要求用户制造网络故障。

维护凭据通过适当的私下渠道提供，不写进公开 Issue。截图可选，公开反馈只保留必要且脱敏的画面。

## 3. 用户反馈与修复闭环

用户可直接在当前 Gate Issue 或对话中粘贴：

> Gate：M?；本次 Site／构建：沿用当前核验包，或填写已变更的信息
> M?-01：通过／失败／阻塞／未测；实际看到：……
> M?-02：通过／失败／阻塞／未测；实际看到：……
> 其余编号：按顺序逐项填写
> 失败或阻塞的操作位置：……；截图或原文链接（可选）：……

不要求用户填技术归属和修复方案，构建者负责转换为可执行任务：

1. 按核验编号、场景及已知原因查找现有反馈 Issue。同一问题更新原 Issue；一个根因影响多个编号时关联多个编号，不重复建单。
2. 失败建立或更新 bug Issue；阻塞建立或更新对应依赖/缺陷 Issue，明确属于外部限制还是代码缺陷。缺少材料的反馈先保留“待定位”，不能直接关闭。
3. Issue 必须补齐：核验编号、场景材料、复现步骤、实际/预期、Site 与版本/commit/dataset、官方来源（如适用）、严重级别、负责模块/处理者、允许修改路径、关联 Gate 和原功能 Issue。截图可选，秘密和私有日志不得公开。
4. 修复限于登记范围；共享接口、迁移、首页骨架或全局样式确需联动时，先在同一任务中列明原因及范围，不能为让检查通过修改权限规则。
5. 修复后注明提交/PR、新 Site 构建与数据版本、构建者自验结果，状态置为“待用户复验”，再次提交原编号的操作和预期。
6. 用户按相同编号确认通过后，才能关闭该反馈并更新 Gate。仅合并 PR、测试通过或等待超时不能关闭；修复 PR 使用关联引用，避免在用户复验前自动关闭反馈。
7. Gate 只有在前门通过、当前全部必测项收到用户通过、反馈修复及复验完成后才可关闭。用户仅反馈部分编号时，其余保持未测。Q5A 的真实外部受限持续如实登记；正确标记和补录策略用例通过后，不因该校尚不能自动采集而阻塞其他已确认交付，也不能把访问限制记为已修复。

严重级别供构建者分级：P0 为越权写入、破坏数据或整个核心流程不可用等立即处置的问题；P1 为必需功能错误或不可用、错误关键事实或无法信任结果；P2 为不妨碍合同内核心使用的改善或表现问题。不能将必需功能失败降为 P2；级别不替代用户复验，后置须有用户明确记录。

## 5. M1：华工、广工的真实招聘流程（M1／D2—D3）

构建者先提供：两校真实公告/活动各有可核对材料；列表已有时段/会场但详情失败的场景；工作地与会场不同的场景；未知字段、日期视图和相关性样例。对应 A01—A10、A12，技术反例的自验结果随包交付。

| 编号 | 用户操作 | 预期 |
| --- | --- | --- |
| M1-01 | 分别选择华工、广工，打开指定招聘记录并核对官方来源。 | 学校归属和原标题正确，记录真实；没有岗位或名单也能看到有效公告。 |
| M1-02 | 查看“列表已有时间地点、详情尚不可读”的指定场景。 | 卡片仍显示已有日期、时段及会场；不会全部写成“原文未披露”。 |
| M1-03 | 对照指定原文查看会场与工作地点。 | 两行含义准确；不把公司名城市、总部或学校所在地当作工作地；未披露不猜测。 |
| M1-04 | 查看普通公告及缺字段的指定记录。 | 普通公告不制造宣讲会场；暂未取得、待核实、未披露、不适用按材料准确表达。 |
| M1-05 | 点击标题进入简要详情，再打开原文及适用附件。 | 核心事实一致、链接正确；已有名单/岗位文本限于本公告，缺详情仍保留事实和原文入口。 |
| M1-06 | 按给定关键词搜索、清空、翻页；编辑未提交条件后翻页，再快速切校。 | 结果遵循已提交条件，不混旧学校、草稿或不同数据版本；无结果有说明。 |
| M1-07 | 依次查看近期、临近、历史、日期未知入口及指定日期范围。 | 样例落在正确视图；发布时间与举办日不混用，历史补录不冒充近期发布。 |
| M1-08 | 比较默认电气列表与“全部招聘”，并检查卡片内容。 | 未知相关性保留，明确无关只在全部招聘；卡片保持已确认字段，没有恢复待遇筛选或独立岗位入口。 |

## 6. M2：十校、维护和人工材料（M2／D4—D5）

构建者先提供：十校状态表、校区依据、受限/无记录场景、维护者进入方式、用于补录/更正/撤回的隔离材料与初始值。写入、幂等、预览绑定、冲突和撤回反例由开发者先验证；用户只在指定隔离数据中操作，不触碰旧生产库。

| 编号 | 用户操作 | 预期 |
| --- | --- | --- |
| M2-01 | 在目录逐一选择固定十校，并对照交付的逐校状态表。 | 十校不替换、不漏项；学校可选与真实接入、收录状态分别表达。 |
| M2-02 | 查看受限或暂未收录学校，再切到正常学校。 | 受限/未检查不写成“学校没有招聘”；正常学校仍可用。按 Q5A 核验处理策略，不认定受限校自动采集通过。 |
| M2-03 | 按样例选择明确校区及未知校区，再切换学校。 | 不混校区；未知另可查看，不算某明确校区命中；华电北京/保定不拆成两所学校。 |
| M2-04 | 在保持 Site 平台登录的情况下进入维护页，再退出业务维护会话，以普通业务访客身份浏览。 | 维护者可操作；退出业务维护会话后只能读招聘信息，不能读取受保护操作资料或保存。未登录 Site 的无痕访问被平台拦截属正常，不能冒充业务写权限验证；服务端拒绝写入的证据由开发者提供。 |
| M2-05 | 粘贴指定官方链接/公开材料，先预览，再明确保存。 | 预览前后访客数据不被提前更改；保存的事实与预览一致，来源可追溯；打不开链接时不能凭 URL 编造内容。 |
| M2-06 | 在指定隔离记录上更正一个字段，查看历史并按说明撤回。 | 更正、理由和依据可追踪；撤回恢复适用值，不清空记录或覆盖后续有效变化。 |
| M2-07 | 查看指定失败来源与待补事项；复查重复保存和冲突场景的展示。 | 能知道哪些需要补材料/重试；重复操作不造重复机会，冲突需重新核对；没有服务器命令或任意写库入口。 |
| M2-08 | 对照本次操作前后的站内摘要，并重看 M1 的代表卡片。 | 新增、官方变化、解析补全、人工更正区分准确；首页骨架与已核验卡片行为没有被来源改动破坏。 |

构建者先提供：至少一次真实自然调度的时间与业务结果、同次 Site 数据/摘要、重复抓取与单源失败证据、隔离恢复结果、v2 只读诊断报告。说明 Site 与实际后端的连接及隔离方式，不公开内部地址或凭据；没有真实调度条件就记相应阻塞，不能用按钮点击或 mock 代替。

| 编号 | 用户操作 | 预期 |
| --- | --- | --- |
| M3-01 | 根据交付包的自然调度前后时间，打开 Site 的来源状态与摘要。 | 最近检查与真实任务记录一致；不是用户打开网页才开始采集，也不把进程退出成功当作全源完整成功。 |
| M3-02 | 对照给定的本次新增/变化清单查看摘要，再复查重复检查场景。 | 新收录与官方新发布、历史补齐、人工更正及解析补全不混算；重复采集不重复计新增。 |
| M3-03 | 查看一处失败/受限来源和一处正常来源。 | 局部失败有真实状态、旧可靠事实仍可读；其他学校的结果不被清空或停住。 |
| M3-04 | 查看没有新增和没有完成检查的两个指定状态。 | “检查后无变化”与“尚未检查/失败/部分成功”可区分，未知不填成零。 |
| M3-05 | 打开开发者完成隔离重启/恢复演练后的指定链接与记录。 | 已提交事实可读且版本/数据身份明确；恢复证据来自真实演练，用户不用执行备份或服务器命令。 |
| M3-06 | 对照提供的只读诊断摘要、Site 交付包和下一次计划。 | 项目明确为 v2，构建/数据一致或有可解释换代记录；状态与计划真实，没有把旧站报告算成新站成绩。 |

每 6 小时调度、健康来源 24 小时检查目标和 48 小时陈旧提示按合同实现。连续 7 个真实自然日的运营观察是后续建议；本周不足 7 日时写实际天数，不伪造未来成功，也不把建议观察期混成已完成的证明。
