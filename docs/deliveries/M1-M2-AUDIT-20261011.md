## 4. #30：状态等待可复现，现场主要耗时仍需测量

### 4.1 重载按钮等待旁路资源

[home.js 37—41、106—131](https://github.com/caor3693-cmyk/Workhunter-v2.0/blob/b17f67d13321bb236728baf51198221f1b58e366/frontend/pages/home.js#L37-L41) 汇总 catalog、updates、opportunities 状态；任一路 loading 时重载按钮禁用。三路请求是并行的，招聘列表先成功就会渲染。

### 4.2 新数据集被旧旁路响应错误标为旧列表

[store.js](https://github.com/caor3693-cmyk/Workhunter-v2.0/blob/b17f67d13321bb236728baf51198221f1b58e366/frontend/state/store.js#L1-L4) 与 [home.js 77—89](https://github.com/caor3693-cmyk/Workhunter-v2.0/blob/b17f67d13321bb236728baf51198221f1b58e366/frontend/pages/home.js#L77-L89) 在三份数据身份不同后统一标旧。

反例：目录/摘要/列表先为 A；提交筛选后仅列表读到 B，目录和摘要仍为 A。B 已成功且符合已提交条件，却被持续标为“上次结果，尚未更新”。再提交 B 不会修复，必须整组重新加载。

应按资源记录新鲜度，对可信的新列表触发有界旁路协调。保留项目、构建、数据模式不匹配警报，以及 dataset/as_of 的分页冲突和晚响应隔离。编辑学校/校区仅改草稿、搜索发一条列表请求、重载使用已提交条件，这三点是正确行为，应保留。

## 6. A-Q：新轮次反复读取前部详情，尾部任务饥饿

相关代码：[discovery.py 82—97、155—175、203—229](https://github.com/caor3693-cmyk/Workhunter-v2.0/blob/b17f67d13321bb236728baf51198221f1b58e366/backend/services/discovery.py#L82-L97)、[ingestion.py 275—317](https://github.com/caor3693-cmyk/Workhunter-v2.0/blob/b17f67d13321bb236728baf51198221f1b58e366/backend/services/ingestion.py#L275-L317)。

普通 refresh 创建新 run_id；待补队列/游标按本轮筛选；列表再次发现记录时将既有任务重新置 pending 并覆盖 run_id；按稳定任务 ID 排序，前部已完成记录优先占掉有限详情预算。

隔离使用真实 ScutAdapter、生产刷新/写入和 SQLite：三个列表页各一条记录，每轮两页/一详情预算，连续三个普通新轮次都请求“第 1 页→详情 1→第 2 页”。详情 1 尝试 3 次，详情 2 尝试 0 次、仍 unknown，第 3 页从未发现。显式 resume 才推进“详情 2→第 3 页→详情 3”。

这证明“单轮有限预算 + 普通连续刷新”不能保证逐步补齐，属于当前采集服务缺陷。扩源会放大它，不能全部推迟给 M3 自然调度。

修复应把稳定任务身份、执行轮次和持续游标区分，兼顾旧待补公平推进与新公告头部发现，保留幂等、失败恢复、分页上限和已取得事实。只提高预算，或永远续跑旧轮而饿死新公告，都不是完整修复。新 Issue #33。

隔离反例按生产函数执行：
