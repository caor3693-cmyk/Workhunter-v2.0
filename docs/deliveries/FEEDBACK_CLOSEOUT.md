# Workhunter：验收反馈、neat-freak 清理与 GitHub 同步规则

生效日期：2026-10-11；管理版本：1.3。适用仓库：`caor3693-cmyk/Workhunter-v2.0`。

本规则落实用户本轮要求：以后每次收到阶段验收反馈，执行者应在处理反馈的同一轮工作中完成局部源码清理、neat-freak 对齐、必要验证和 GitHub 同步，再交付原编号复验。它是会话/任务执行规则，不代表已经设置无人值守的 GitHub 监听或定时任务。

入口为既有 `AGENTS.md → docs/STATUS.md → 本文件`。开始开发、接收反馈、修复收尾或提交新候选前必须读取；产品范围、字段证据和模块边界继续遵守 PRODUCT/CONTRACTS/TASKS。若用户后续明确改变本次任务范围，记录该决定并按新范围执行。

## 1. 收到反馈就建立可追踪的处理记录

1. 读取当前 STATUS、原 Gate、相关功能/反馈 Issue、最新用户评论及交付材料，确认反馈对应的 Site、源码提交、后端构建、dataset/data_mode 和发生时间。无法取得的身份明确标未知，不拿旧交付身份补充为当前实测。
2. 保留原 `Mx-yy` 检查编号及用户原意。用户只反馈部分项目时，其他项目维持未测或既有有效结论；用户沉默不视为通过。若用户当前明确授权“未指出问题的项目默认通过”，按其指定本轮范围登记并记录原话与来源，保留历史结论；这是明确用户决定，不是沉默推断。2026-10-11第二轮仅M0/M1采用此例外，结果见[M0/M1第二轮报告](M0-M1-FEEDBACK2-20261011.md)，不推广到未实施阶段。
3. 按现象、模块、根因查重。同根因更新原 Issue；不同根因才新建。功能本来属于未实施阶段时，补入已有工作包，不重复建同一功能单。
4. 记录预期/实际、可复现步骤、影响、优先级、对应 Issue/检查点、根因证据或待定位项。源码推断、隔离反例、现场观察和用户实际结果分别标明。
5. 更新当前事实与阶段状态；历史截图、原始反馈和旧候选留在交付记录，STATUS 保持简明当前结论。真实失败不得改写成正常空态或历史测试成功。

## 2. 限定范围修复，保持连续推进

- 先登记本批 Issue、工作包、实际 PR base/head、允许路径、共享文件整合者和受影响检查点，再修改代码。
- 修复当前反馈及其必要依赖。共享 API、迁移、构建、页面壳或样式确需联动时写明原因，由同一整合者处理；通过可信治理流程补范围，不能在业务分支里改 checker/规则表给自己放行。
- 保留现有技术栈、已确认产品选择和模块职责。不要借反馈清理进行全站改版、依赖升级、重命名工程或后置功能扩张。
- M0 发出复验后继续独立 M1 工作；失败反馈优先插入相应模块。人工验收仍按 M0→M1→M2→M3→M4，工程并行不等于跳过用户 Gate。
- 当前任务已经授权的修复、可逆局部清理、文档更新、工作分支提交/推送和核对连续完成，无需每次另问“是否清理/是否同步”。只有确切权限阻塞、不可恢复操作或超出既有任务范围的决定才暂停相应动作，并说明依据；其余独立工作继续。

## 3. 每次修复后的局部源码清理

功能修复完成后，检查本批修改文件及直接关联文件，移除已经无用的导入、变量、分支、调试输出、重复且可安全合并的局部逻辑、失效注释和误导性阶段文案。保留有用的错误诊断、未知状态、数据校验和回归用例。

清理以可解释的小差异进行；大范围格式化、无关文件改写、删除测试、升级框架/依赖不属于默认清理。会改变业务行为的调整按修复记录和验证，不能用“只是 cleanup”掩盖风险。没有必要的清理项时，记录“已检查，无需改动”，不制造空提交或凑改动量。

功能与清理可以分别提交，或在紧密相关时同一提交说明清楚；每个提交均须可归属到当前工作包。先清理再运行最终相关回归，不能清理后沿用之前的绿色测试结果。

## 4. 使用 neat-freak 对齐六类事实

执行时发现并完整读取实际可用的 `neat-freak/SKILL.md` 及它要求的参考文件，记录来源和版本。不得仅凭名称声称运行过，也不在没有任务需要时自行安装、升级或改写全局 skill。

本轮规则依据：已读上游 [KKKKhazix/khazix-skills/neat-freak](https://github.com/KKKKhazix/khazix-skills/blob/main/neat-freak/SKILL.md)，其声明版本为 **3.0.0**，所读 SKILL blob 为 `51333e97c010a8ba13b10dc3c89d17021d915aa8`，并读取 agent-paths、verification、governance、sync-matrix 四份参考。这是制定规则时的历史依据。本轮实际执行已完整读取本机 `C:/Users/曹睿/.codex/skills/neat-freak/SKILL.md`，声明版本 **3.0.1**，SHA-256 `fb645274f18473740b389efb89b51ef4e58ddefaf26a4b1b43a9d82e4c848b31`，并读取上述四参考；各批六面证据随交付记录保留。后续仍以实际读取版本为准。若没有可读取的 skill，先完成本规则中已授权的清理/验证/同步，明确标记 skill 缺失，不假称已调用或让其他工作无理由中断。

neat-freak 用于对齐项目事实；第 3 节的源码清理是用户另外明确要求的执行步骤。两者都要检查，不能只改文档就声称代码已经清理。

| 事实类别 | 每次应核对的内容 | 不得混淆 |
| --- | --- | --- |
| 代码 | 当前分支、完整 SHA、实际 diff、局部清理、测试与范围结果 | 测试通过不表示功能已让用户通过 |
| 运行 | 实际 Site 来源、前后端构建、同源 GET、dataset/data_mode、运行时间 | 已推送源码不等于 Site 已更新；历史成功不等于当前恢复 |
| 文档 | README 运行方式、STATUS 当前结论、相应合同、Issue、BOARD/ROADMAP/config | 计划目标、工程完成、用户结果、正式发布分开 |
| 规则 | 当前任务入口、范围规则、读取链、检查点编号一致 | 历史 S/G 证据保留；M/W/F/D/O 稳定标识不任意改号 |
| 记忆 | 只核对当前授权可见的项目上下文是否与新证据冲突 | 不修改无关长期记忆、全局助手规则或私人记录 |
| 工作区 | 未提交改动归属、临时产物、重复副本、用户证据与运行资产 | 清理临时副本不等于可以删除唯一证据、数据库或未合并工作 |

本规则不授权删除/重建数据库、备份、唯一截图、原始材料、凭据、用户未提交改动或未合并分支，也不授权清理其他项目。可再生且属于本轮的临时文件可按既有授权清理；需保留的资产写明位置与原因，不为了“零残留”删除。

## 5. 清理后做足够且有针对性的验证

根据实际差异运行必要的领域/API/代理/前端用例，并补能复现根因的反例。涉及核心写事务、只读边界或共享查询时运行相关完整套件；纯文档修改检查链接、配置、编号、差异与范围即可，不以反复全量测试充当工作量。

从可信目标执行工作包范围检查，覆盖整个 PR；记录 base/head、包和路径。目标缺规则或校验失败时修复治理前置，不跳过检查或把所有 PR 都当 W00。

页面/运行变动还需构建、真实 Site 请求及受影响浏览器操作；采集变动需真实官方来源→证据→入库→API→页面。隔离样例与实际材料分别标记。只完成 HTTP 探测不能声称完成浏览器登录、390px 或用户验收。

任何失败写明发生层、实际结果、影响和下一步；保留待处理状态。已验证的无关部分不用重复扩大检查。命令未运行、执行环境阻塞和测试失败分开记录。

## 6. 完成 GitHub 同步并回读

1. 回读 origin、当前分支、远端 head 和工作区。先保护用户已有改动；只暂存本批明确路径，不把整个目录盲目加入提交。
2. 提交说明写清问题、修改结果和必要验证；PR 用 `Refs #…`，用户未复验前不用自动关闭 Issue 的关键词。优先使用当前合适的工作分支/PR，避免重复建单建 PR。
3. 向已授权工作分支正常推送，或用带 expected SHA 的 GitHub ref 更新；不自动 force push、改默认分支、合并 PR 或删除分支。远端并发前进时先回读差异并整合，不能覆盖他人提交。
4. 回读远端完整 SHA、PR head/base、实际差异和 CI。确认本地交付内容与远端一致；CI pending、failure、无可用记录必须如实说明，不能仅看到 push 成功就报“同步验证完成”。
5. 同步相关 Issue、STATUS、仓库 BOARD/ROADMAP 和 `config/project.json` 的当前状态、目标/实际日期、依赖与证据。原生 GitHub Projects 仅在工具可用且实际更新成功时声称同步；当前 #19 未解决时使用仓库索引并标明限制。
6. 应用变化的私有验收候选按既有授权与发布流程从干净提交构建、保存并实测；记录它实际使用的代码与数据身份。纯计划、反馈登记或文档清理无需重新发布。正式上线继续受 #18 与全部用户 Gate 约束。

仓库中的记录以稳定提交/PR 链接或实际源码提交为准，不把文档自己尚未生成的提交 SHA 写成已验证事实。最后一次推送及 CI 的回执可以写入 PR/交付回复，避免为自引用 SHA 不断生成文档提交。

## 7. 交付复验与关闭条件

修复和必要自验完成、候选可达后，Issue 可进入 `Awaiting verification`，仍保持 open；附同编号的点击路径、应见结果、指定材料与新构建。当前历史失败记录保留，新增“待复验”工程状态，不代填用户结论。

只有用户按对应编号确认通过，且必需范围和回归满足，才能关闭反馈/功能 Issue；阶段单还必须满足前序 Gate 和本阶段完整清单。某次用户通过的候选被改动时，对受影响检查点重新提供回归/复验材料，不能继续用过期通过支撑发布。

每次回执至少包含：

- 本次反馈编号、根因、修改结果；修复/局部源码清理实际涉及的路径。
- neat-freak 实际来源/版本，以及六类事实中完成、未涉及、阻塞的部分。
- 必要验证、准确失败/未执行项，远端完整提交、PR 和 CI 结果。
- 实际 Site 与后端/dataset 身份；若本次未更新或读取失败，直接写明。
- 原编号复验入口、用户结论保持情况、剩余问题与独立后续工作。
